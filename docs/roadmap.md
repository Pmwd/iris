# Iris 路线图（v8 之后）

> 状态：M0 T4–T6 真实验收通过；M1 最小可观测已实现；M2 冒烟 5/5 通过（其余案例待执行）  
> 更新时间：2026-11-24  
> 本文件：后续方向讨论机制、可观测计划、全局系统大盘、里程碑与优先级  
> 当前阶段：`CURRENT_PHASE.md` · 历史路线：`docs/roadmap-history.md` · 决策：`docs/decisions/` · 验收：`docs/acceptance/`

## 0. 一句话结论

Iris 已经完成从“Task 工作台”到“Session 工作台 + 三层记忆 + SDK 审批”的转身。接下来不是继续加角色或功能，而是：

1. **先把 v8 用真实 SDK 跑稳**（M0，T1–T6）；
2. **建立最小可观测**（M1：Token、耗时、成功率、健康；暂不做告警）；
3. **先验证记忆质量，再做全局大盘**（M2 → M3）；
4. **最后再投入 Scholar 深度与产品体验**（M4 → M5）。

顺序原则：

- 没有可观测就做优化，会变成凭感觉加功能。
- 记忆是 Iris 的核心差异化；先用 10–20 个真实案例验证摘要/事实/召回，再决定大盘展示哪些记忆信号。否则容易做出“指标好看但记忆没用”的仪表盘。
- 大盘建立在 M1 指标与 M2 结论之上，而不是反过来驱动记忆工作。

## 2. 方向讨论机制（后续方向交流）

### 2.1 原则

- **证据优先**：方向提案必须引用真实使用、指标或可复现实验，而不是“架构上更好”。
- **最小可逆**：默认先做小实验；不可逆、跨模块或涉及安全/隐私/成本的改动必须写 ADR。
- **一次只验证一个假设**：不同时加角色、检索、应用和多 Agent。
- **明确不做什么**：每个阶段都写暂缓清单，防止范围蔓延。

### 2.2 评审节奏

| 节奏 | 输入 | 输出 |
|---|---|---|
| 每个里程碑结束 | 大盘指标、真实 CLI 验收、用户摩擦 | 继续 / 调整 / 暂停该方向 |
| 每周（可异步） | 24h/7d 指标、最近失败、候选事实 | 本周是否值得改代码；是否触发告警 |
| 每季度 | 角色边界、记忆质量、成本、数据体积 | 是否新增角色/应用/后端；是否引入语义检索 |

### 2.3 方向提案模板

任何新方向先填这张表，再决定是否进入里程碑：

| 项 | 要求 |
|---|---|
| 问题 | 用户现在具体卡在哪里？发生在哪个角色/会话？ |
| 证据 | 真实会话、指标、验收记录或实验数据 |
| 用户价值 | 减少重复解释 / 提高成功率 / 降低成本 / 降低风险 |
| 方案对比 | 至少两个可行方案，含“不做” |
| 可逆性 | 能否用配置/开关回滚？是否改 schema/API？ |
| 成本与风险 | CLI 成本、维护成本、安全/隐私影响 |
| 验证指标 | 一个主指标 + 一个护栏指标 |
| 停止条件 | 什么数据出现就暂停或放弃 |

### 2.4 实验模板

- **假设**：`如果我们做 X，那么 Y 指标会从 A 改善到 B，因为 Z。`
- **最小实验**：只改一个变量；优先 fake CLI + 临时数据目录；真实 CLI 实验设成本上限。
- **样本**：至少 10–20 次真实 Turn，或 20–30 条真实查询。
- **成功/停止**：提前写清楚；不因“看起来还行”而继续。
- **记录**：实验结论写入 `docs/evaluation/`；影响架构的写入 ADR。

### 2.5 决策与 ADR

以下情况必须写 ADR：

- 改 schema、核心 API、权限模型、数据保留/删除策略；
- 引入外部服务、向量库、多进程/多后端；
- 改变“什么进入记忆”的规则；
- 任何不可逆或难以回滚的改动。

ADR 状态：`提议 / 已采用 / 已取代 / 已放弃`。方向被放弃也要记录原因。

| 编号 | 问题 | 当前倾向 | 需要的证据 |

## 4. 可观测计划（Observability）

### 4.1 目标：回答五个问题

1. **是否健康？** CLI 安装/认证、数据库可写、worker 是否卡住、磁盘是否充足。
2. **在做什么？** 当前活动会话/Turn、最近失败、队列等待。
3. **花了多少？** 每 Turn / 会话 / 天 / 角色的 CLI 报告成本与 token。
4. **记忆是否健康？** 摘要覆盖、摘要滞后、候选/接受事实、注入率、事实使用。
5. **哪里在变坏？** 错误分类、取消/中断率、resume 失败率、存储增长。

### 4.2 信号模型

| 域 | 信号 | 数据来源 | 保留 |
|---|---|---|---|
| Turn 生命周期 | 创建/开始/结束、状态、mode、权限档位 | `turns` | 与 Turn 同寿命 |
| CLI 进程 | spawn 失败、退出码、超时、取消、resume 失败 | `turns.error_type`、`turn_events` | 同上 |
| 工具与权限 | 工具调用数、权限拒绝、坏 JSON | `turn_events.kind` | 同上 |
| 成本/Token | CLI 报告 cost/usage | `turns.cost_usd`、`usage_json` | 同上 |
| 摘要 | 生成/失败、覆盖 turn、耗时、成本 | `session_summaries` | 长期 |
| 事实 | 候选/接受/拒绝、来源、置信度、使用次数 | `facts`、`fact_extractions` | 长期 |
| 注入 | 注入了哪些事实、字符数、是否注入摘要 | `turns.prompt_manifest_json` | 与 Turn 同寿命 |
| 存储 | DB 大小、WAL、原始日志、备份年龄 | 文件系统 + `PRAGMA` | 快照长期 |
| 健康 | CLI 版本/认证、DB、内存 worker 队列 | 健康探针 + 内存状态 | 实时 |

**原则**：指标只存计数、时长、成本、状态和错误类型；**不存消息内容、事实正文、工具输入输出、prompt**。原始日志仍只在本机，大盘只显示体积。

### 4.3 指标字典

| 指标 | 定义 | 来源 |
|---|---|---|
| `active_turns` | `status in (starting,running,canceling)` 的 Turn 数 | `turns` |
| `stuck_turns` | 活动 Turn 且 `started_at < now - run_timeout` | `turns` |
| `turn_success_rate_24h` | succeeded / 终态 Turn（24h） | `turns` |
| `turn_duration_p50/p95` | `ended_at - started_at` 的分布 | `turns` |
| `queue_wait_p95` | `started_at - created_at` 的分布 | `turns` |
| `resume_rate` | `mode=resume` / Turn | `turns.mode` |
| `resume_failure_rate` | resume 中 failed / resume | `turns` |
| `cancel_rate` / `interrupt_rate` | canceled / interrupted ÷ 终态 Turn | `turns` |
| `tool_calls_per_turn` | `tool.use` 事件数 / Turn | `turn_events` |
| `tool_denial_rate` | 含 `permission.denied` 的 Turn / 有工具调用的 Turn | `turn_events` |
| `cost_24h` | Σ `cost_usd`（标注为 CLI 报告值） | `turns` |
| `cost_per_success` | cost_24h / succeeded Turn | `turns` |
| `cost_by_session` | 按会话聚合成本 | `turns` |
| `summary_lag` | `max(turn.seq) - sessions.summary_covers_turn_seq` | `sessions`、`turns` |
| `summary_failure_rate` | failed / 已完成摘要 | `session_summaries` |
| `summary_coverage` | 有 succeeded 摘要的会话 / 有终态 Turn 的会话 | `sessions`、`session_summaries` |
| `fact_candidates_pending` | `facts.status='candidate'` | `facts` |
| `fact_accept_rate` | accepted / (accepted+rejected)（已审核） | `facts` |
| `fact_injection_rate` | 注入 ≥1 事实的 Turn / Turn | `turns.prompt_manifest_json` |
| `fact_use_top` | 按 `use_count` 排序的已接受事实 | `facts` |
| `extraction_success_rate` | succeeded / 提取任务 | `fact_extractions` |
| `db_size` / `raw_log_size` | 数据库 / `session_logs` 体积 | 文件系统 |
| `backup_age` | 最近备份距今 | `data/backups` |
| `disk_free` | 数据目录所在盘剩余空间 | 文件系统 |
| `error_top` | 按 `error_type` 聚合最近失败 | `turns` |

### 4.4 实现阶段

**O1 — 指标层 + 健康/错误 API（M1，✅ 已实现 2026-11-24，不改 schema）**

- 新增 `backend/app/services/metrics.py`：用 SQL 聚合上述指标；结果内存缓存 10 秒。
- 新增 `GET /api/metrics/overview?role=&project_id=&range=24h|7d|30d`。
- 新增 `GET /api/metrics/health`：CLI 探针、DB 可写、活动 Turn、worker 队列。
- 新增 `GET /api/metrics/errors?limit=20`：只返回 `error_type`、时间、会话/Turn id、截断后的短消息。
- 同时埋记忆相关计数：事实注入率、事实使用 Top、摘要成本与滞后，供 M2 使用。
- 暂不做 `timeseries`、rollups 和告警；M1 的目标是能手工查数、能对账。
- 测试：用 seeded fake CLI 数据核对 SQL 聚合；范围过滤；不泄露内容。
- 验收：`docs/acceptance/m1-observability.md`（3 个指标测试，全量 45 个后端测试）。

**O2 — 滚动汇总（M3 大盘前，约 3–5 天）**

- 新增 `metric_rollups(id, bucket_start, bucket_size, metric, dimensions_json, value, updated_at)`。
- 启动时与每 5 分钟执行一次轻量 rollup：小时/天粒度的 Turn 数、成功率、成本、摘要/事实计数、存储快照。
- 目的：大盘趋势不扫全表；原始事件/日志即使清理，历史指标仍保留。
- 同时补 `GET /api/metrics/timeseries` 供大盘使用。
- 保留策略：rollups 365 天；原始 JSONL 默认 90 天（`IRIS_RAW_LOG_RETENTION_DAYS`）；备份保留策略见维护文档。

**O3 — 告警规则（暂缓到 M3 之后；先手工看指标）**

| 规则 | 条件 | 级别 |
|---|---|---|
| CLI 不可用 | 未安装或未认证 | critical |
| Turn 卡住 | `stuck_turns > 0` | critical |
| 数据库异常 | 健康检查 DB 不可写 | critical |
| 摘要连续失败 | 最近 3 次摘要失败 ≥ 2 | warning |
| 提取失败 | 最近 1 次提取 failed | warning |
| 摘要滞后 | `summary_lag > 2 × trigger_turns` | warning |
| 事实接受率低 | 最近 20 条已审核接受率 < 30% | info |
| 错误率上升 | 24h 终态错误率 > 20% | warning |
| 存储增长 | raw_logs > 5 GB 或磁盘剩余 < 2 GB | warning |
| 备份过期 | `backup_age > 7 天` | warning |
| 成本超预算 | 24h 成本 > 配置预算 | warning |

### 4.5 隐私与保留

- 指标与告警**不包含**消息、事实正文、prompt、工具输入输出。
- 错误消息只保留 `error_type` + 截断短消息；不写凭据、路径中的敏感片段需脱敏。
- 成本是 CLI 报告值，不是账单；大盘必须标注。
- 原始 JSONL 仅本机；大盘只显示体积与最近写入时间。
- 删除会话时同步删除其原始日志目录；rollups 不含会话内容。

### 4.6 验收

- [ ] 用固定 fake CLI 数据集，overview 的每个数字能与手工 SQL 对上。
- [ ] 24h / 7d / 30d 与 role/workspace 过滤正确。
- [ ] `stuck_turns`、摘要滞后、提取失败能被模拟触发并出现在健康/错误 API 中（告警规则暂缓）。
- [ ] 指标响应不包含任何消息/事实/工具内容。
- [ ] 大盘在空库、仅旧数据、部分失败数据下不崩溃。

## 5. 全局系统大盘（M3）

> 前置：M1 指标层完成，M2 已给出“哪些记忆信号值得展示”的结论。大盘不是用来驱动记忆工作的，而是把已验证的指标和记忆结论可视化。

### 5.1 位置与入口

- 新路由 `/dashboard`；侧栏底部增加「系统大盘」。
- 与「记忆库」「工作区」并列；不替代聊天主界面。
- 刷新：10 秒轮询；顶部显示“最后更新”；后续可选 SSE。

### 5.2 信息架构（一屏优先）

1. **状态条**：CLI 安装/认证、DB、worker、磁盘、活动 Turn、最后更新时间。
2. **KPI 卡片（8 个）**：24h Turn 数、成功率、p95 时长、队列等待、24h 成本、摘要滞后、候选事实、今日错误数。
3. **活动与质量**：
   - 24h/7d Turn 按状态堆叠图；
   - 最近失败（error_type、会话、时间）；
   - resume 失败率、取消/中断率。
4. **成本**：
   - 成本趋势（天）；
   - 成本最高的会话；
   - 每次成功 Turn 的平均成本；
   - 标注“CLI 报告值”。
5. **记忆**：
   - 摘要覆盖率与滞后；
   - 候选/接受/拒绝趋势；
   - 事实注入率与 Top 使用事实；
   - 提取任务成功率。
6. **存储**：
   - DB / WAL / 原始日志 / 备份体积；
   - 30 天增长趋势；
   - 保留策略与清理入口（只读展示，清理走维护命令）。
7. **告警列表**：级别、规则、触发时间、跳转到相关会话/Turn。
8. **趋势**：7/30 天小图；点击进入对应范围。

### 5.3 交互

- 范围切换：24h / 7d / 30d。
- 过滤：角色（Coding/Scholar）、工作区。
- 下钻：KPI/图表 → 会话列表 → 会话聊天；错误 → Turn 原始日志；候选事实 → 记忆库。
- 空状态：没有数据时显示“创建第一个会话 / 结束会话生成摘要 / 提取事实”的引导。
- 错误状态：单个指标失败不影响其它区块；显示局部错误与重试。

### 5.4 API（大盘组合层）

## 6. 记忆质量与检索（M2）

### 6.0 真实案例集（10–20 个）

先做一组可重复的真实案例，作为后续所有记忆改动的基线。案例集见 `docs/evaluation/memory-benchmark.md`（19 个案例；**冒烟 A1/B1/B4/C1/C3 已通过**，其余待执行）。

| 类别 | 建议数量 | 观察点 |
|---|---|---|
| 摘要保留 | 4–6 | 目标、已完成、决策、未决问题、产出/文件、失败教训是否保留；是否编造 |
| 事实提取正确性 | 4–6 | 候选是否过度概括、把假设当事实、缺来源；接受率与重复率 |
| 跨 Session 召回 | 3–5 | 新 Session 是否注入相关事实/摘要；无关请求是否被错误注入 |
| 重复/冲突/过期 | 2–4 | `supersede` 是否正确；旧事实是否被归档；冲突是否暴露给用户 |

每个案例记录：输入、期望、实际注入清单（manifest）、人工判断、成本/耗时。

**验收**：

- [ ] 10–20 个案例可在固定数据目录重放。
- [ ] 每个案例有明确期望与实际观察，不只看“感觉还行”。
- [ ] 结论能回答：摘要是否够用、事实是否可信、召回是否命中、冲突是否可控。
- [ ] 根据结论决定是否调整阈值/prompt/检索，而不是直接进入大盘或 Scholar。

### 6.1 摘要质量

- 评估维度：目标/已完成/决策/未决问题/产出/失败教训的覆盖；是否编造；是否保留关键路径与测试结果。
- 方法：抽样 10–20 个真实会话，人工 1–5 分；对比不同阈值与 prompt。
- 指标：摘要覆盖率、滞后、人工评分、摘要成本占比、摘要后事实提取的接受率。

### 6.2 事实质量

- 指标：候选接受率、重复率、update/supersede 比例、错误类型（过度概括、把假设当事实、缺来源）。
- 改进顺序：prompt 约束 → 指纹/相似度去重 → 合并/拆分 → 人工审核体验。
- 不做：自动接受；不做人格推断；不把网络内容直接写成事实。

### 6.3 检索

- 现有：FTS5 + 中文 bigram + 停用词 + 别名 + LIKE 回退 + 预算。
- 评估集：20–30 条真实查询（含改写、跨语言、项目/全局混合）。
- 指标：recall@k、错误注入率、注入字符成本。
- 触发语义检索的条件：在评估集上 recall 明显不足（建议 < 60–70%），且别名维护无法弥补；否则先扩别名与停用词。
- 若引入：优先本地、可回滚的 embedding；仍需预算与人工可见的注入清单。

## 7. Scholar 深度研究方向（M4）

- **第一步先验证增量价值**：用 5–10 个真实研究问题对比「Scholar 聊天 + Web」与普通聊天/手工搜索，记录来源质量、耗时、返工与成本。
- 目标：把旧的 research 编排能力迁到 Session 之上，而不是恢复旧 Task 模型。
- 形态：父 Scholar Session → 受控子会话/子 Turn（read-only/research，独立上下文）→ 并发上限 → 来源保留 → 父会话汇总为摘要 + 候选事实。
- 指标：子任务成功率、来源覆盖率、每研究任务成本、耗时、产生的事实接受率。
- 门槛：聊天 + Web 的 Scholar 在真实任务中不足，且大盘显示研究类会话有明显失败/返工。
- 不做：自建搜索/爬虫/排序；不受控子 Agent；自动把研究结论写成事实。

## 11. 成功指标与决策触发

### 11.1 领先指标

- 首次使用到第一个会话的时间。
- 每个会话的有效 Turn 数。
- resume 成功率。
- 摘要覆盖率与滞后。
- 事实接受率与注入命中率。
- 每次成功 Turn 的成本。
- 用户重复解释的减少（定性复盘）。

### 11.2 护栏指标

- 无凭据/消息/事实内容进入指标或日志。
- 无自动接受事实。
- 无孤儿进程、无卡死活动 Turn。
- 无数据丢失；备份年龄可控。
- 任何阶段都能停止且不破坏旧数据。

### 11.3 决策触发（示例）

| 如果看到 | 那么优先做 |
|---|---|
| resume 失败率 > 5% | 改进 compact/恢复路径；检查 CLI 版本 |
| 摘要成本 > 总成本 20% | 调整阈值/输入长度/摘要模型 |
| 事实接受率 < 30% | 改进提取 prompt、去重与审核体验 |
| 注入命中率 < 50% | 扩别名、停用词；评估语义检索 |
| 24h 有 stuck Turn | 先修 supervisor/锁，不加新功能 |
| 错误率 > 15% | 暂停新方向，先稳定 |
| 大盘某指标无人使用 | 删除该指标，保持一屏可读 |
