# Phase 2 真实使用观察

> 目标：用当前版本积累真实任务，判断上下文推荐是否真的减少重复解释。  
> 原则：先观察，不为了指标增加新功能；记录事实和主观判断，不把模型推测当作用户事实。

## 1. 定义

**跟进任务（follow-up task）**

一个任务的目标依赖之前任务的结果、决策或项目约定。只有跟进任务才能检验上下文复用。

**重复解释（repeated explanation）**

用户不得不再次说明一个已经存在于以下位置的信息：

- 项目 brief；
- 已被用户接受的 note；
- 之前任务已经确认的决策、命令、文件位置或约束。

仅仅补充新信息不算重复解释。

**有效上下文**

被推荐的 note 中，用户愿意保留，并且任务实际使用了其中的信息。保留但未使用不算有效。

## 2. 任务粒度与分类

### 2.1 什么是 Task

Task 是**用户会独立创建、审查和接受**的工作单元，不是一次模型调用、一个工具步骤或一条 note。

- “增加分类过滤”是一个 Task。
- “运行测试”“读取文件”“写测试”是 Task 内的 Run/步骤，不单独算 Task。
- 同一个目标可以经历多次 Run（失败、恢复、重试），仍属于同一个 Task。
- 当前版本中，Task 进入 `needs_review` 后不能再追加 Run；因此需要新目标时创建新 Task。

### 2.2 三类任务

| 类型 | 定义 | 是否计入跟进任务 |
|---|---|---|
| 独立上下文任务 | 新目标，只依赖项目 brief 或全局偏好 note，不依赖之前任务的结果 | 否；用于检验偏好/全局上下文注入 |
| 跟进任务 | 新目标，且依赖之前任务的结果、决策、文件位置、清单或已接受 outcome | 是；用于检验任务间上下文复用 |
| 验证重跑 | 为验证代码/检索修复，把同一场景重新执行一遍 | 否；不重复计入样本 |

### 2.3 当前任务分类

| 任务 | 类型 | 依赖 |
|---|---|---|
| Expense CLI / Add category filtering to CSV export | 跟进 | CSV export outcome |
| 生活助手 / 本周水果采购清单 | 独立上下文 | 全局水果偏好 |
| 生活助手 / 把水果清单改成两人份 | 跟进 | 水果采购清单 outcome |
| 生活助手 / 本周全身训练计划 | 独立上下文 | 全局健身偏好 |
| 生活助手 / 推荐三本符合偏好的书 | 独立上下文 | 全局阅读偏好 |
| 生活助手 / 六人聚会水果拼盘 | 跟进 | 水果偏好 + 之前的水果清单 outcome |
| 三个标记为“修复验证”的任务 | 验证重跑 | 对应原任务和修复后的检索逻辑 |

所以“本周全身训练计划”和“阅读推荐”是真实任务，也是全局偏好注入的有效样本，但**不是跟进任务**：它们没有依赖之前某个任务的产出。它们证明的是“个人偏好能被正确选中”，而不是“上一个任务的成果能被复用”。

## 3. 观察字段

每次跟进任务记录：

| 字段 | 说明 |
|---|---|
| 日期 | 实际执行日期 |
| 项目 / 任务 | 项目名和任务标题 |
| 依赖的前序任务 | 哪个任务或哪条 note 提供了上下文 |
| 推荐 note | scope、标题、reason（pinned/matched/recent） |
| 用户调整 | 接受了哪些推荐、手动加了哪些、移除了哪些 |
| 是否重复解释 | 是/否；如果是，具体重复了什么 |
| 缺失上下文 | 是否漏掉了关键 note；是什么 |
| 结果 | 任务是否完成、测试/验证结果、耗时或成本（可选） |
| 判断 | 推荐有用 / 一般 / 误导 |

## 3. 试点成功标准

样本量小，不追求统计显著性。建议先积累 **5 个真实跟进任务，跨至少 2 个项目**，然后复盘：

- 至少 70% 的跟进任务没有发生重复解释；
- 每个任务最多出现 1 次关键上下文遗漏；
- 用户主观判断“推荐有用”的次数多于“误导”；
- 没有因为推荐错误导致任务失败或错误修改。

如果达不到，优先调整：

1. 推荐权重（相关度/最近/使用次数）；
2. 预算和截断策略；
3. 中文检索/分词；
4. note 的质量和标题写法。

而不是先增加角色或应用。

#### 试点 1 补充事实

- 上下文预览自动选中 `CSV export outcome`，reason=`matched`，预算 4000 tokens，预计约 390 tokens。
- 运行 manifest `selection_mode=auto`，实际注入该 note；运行后 use_count 从 0 变为 1。
- 实际 diff 只修改 `expense.py` 和 `tests/test_expense.py`；模型明确复用现有导出路径。
- CLI 报告成本约 `$0.1441`。
- 结果已接受为 `Category filtering outcome` note；任务标记完成。
- 本次任务目标仍包含“复用现有实现 / 不加依赖”，这是一次可以省略的重复约束。下一次试点应尽量只写新需求，观察模型是否仅靠 note 就能保持既有约束。

### 关键发现：pinned 全局 note 过度注入

三次任务的上下文预览都选中了同样的 4 条：

- 水果偏好（示例）[global/pinned]
- 健身偏好 [global/pinned]
- 阅读偏好 [global/pinned]
- 两人份水果清单 outcome [project/matched]

问题：

1. **pinned 被当作无条件注入**：三个不同主题的全局偏好都进入了每个任务。输出虽然能忽略无关内容，但浪费预算，也增加误用风险。
2. **中文任务词导致误匹配**：`两人份水果清单 outcome` 在健身/阅读任务中被标为 `matched`，很可能是“本周”等通用词命中；实际无关。
3. 当前规则下，用户置顶的偏好越多，每个任务的上下文越嘈杂，推荐精确度会下降。

建议的修正方向（需要确认后再改）：

- 将 pinned 从“无条件注入”改为“排序加权”；另设明确的“always include”能力，并限制数量。
- 对全局 note 增加相关性门槛；只有匹配时才注入，除非用户显式选择。
- 扩充中文任务停用词（本周、每次、分钟、输出、说明、不要、修改等），减少通用任务措辞造成的误匹配。
- 或在每类偏好上增加 domain/category，让任务只激活相关类别。

### 修复后验证（2026-10-23）

修正内容：

- pinned 只增加排序分，不再绕过相关性自动注入；
- 自动选择要求本地关键词/中文 bigram 实际命中；
- FTS rank 只作为命中后的排序加分；
- 中文查询按 bigram 切分，并过滤数字、通用任务词和功能字 bigram；
- UI 提示改为“置顶优先排序，不强制注入”。

三个验证任务（`needs_review`，未接受为 note）：

| 生活助手 / 六人聚会水果拼盘（修复验证） | 4 条 | 3 条：水果偏好 [global/pinned] + 两份相关水果清单 [project/matched] | 采购量/摆盘建议，排除芒果和榴莲 |

## 6. 辅助报告

在仓库根目录运行：

```powershell
.\.venv\Scripts\python.exe scripts\context_report.py
```

脚本只读 SQLite，汇总：

- 每个任务的运行；
- 实际注入的 note、scope、reason；
- 推荐 ID 与手动选择的差异；
- note 使用次数和最近使用时间。

报告用于辅助记录，不替代用户对“是否重复解释”的判断。只在积累了真实任务后才有意义。
