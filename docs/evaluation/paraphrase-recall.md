# 语义改写召回实验（含 aliases 对比）

> 日期：2026-10-23  
> 目的：验证“措辞不同但语义相关”的 note 是否会被当前 FTS5 + 中文 bigram 检索漏掉，并比较用户维护 aliases/tags 后的召回。  
> 方式：只读、临时数据库；不调用真实 CLI，不修改真实数据。  
> 脚本：`scripts/paraphrase_recall.py`

## 1. 方法

每个样例创建一个临时数据库、一个已接受全局 note 和一个任务，然后调用真实的 `collect_candidates` 与 `search_global_notes`。

- **Control**：任务与 note 共享明确关键词，预期可命中。
- **Paraphrase**：语义相关但使用不同措辞，预期也应命中。
- 使用全局 note，避免“最近项目 note”回退掩盖检索问题。
- 只测自动推荐；不测用户手动勾选。
- 两种模式：
  - `plain`：note 不带 aliases，等价于原有关键词/bigram 检索。
  - `aliases`：note 带用户维护的别名/标签，例如 `安全,聚会,饮食禁忌`。

## 2. 结果

```text
PLAIN_CONTROL_RECALL     5/5
PLAIN_PARAPHRASE_RECALL  0/5
ALIASES_CONTROL_RECALL   5/5
ALIASES_PARAPHRASE_RECALL 5/5
```

同一组 10 个用例，别名只加在 note 侧；任务查询和其措辞不变。

| 类型 | Note 内容 | 任务意图 | 结果 |
|---|---|---|---|
| Control | 对芒果严重过敏 | 芒果过敏 | 命中 |
| Paraphrase | 对芒果严重过敏 | 聚会准备安全食物，避免身体不适 | **漏召回** |
| Control | 偏好全身锻炼 | 全身训练 | 命中 |
| Paraphrase | 偏好全身锻炼 | 杠铃复合动作训练 | **漏召回** |
| Control | 文笔细腻、情感克制的言情小说 | 文笔言情 | 命中 |
| Paraphrase | 文笔细腻、情感克制的言情小说 | 文字质量高、感情线好的书 | **漏召回** |
| Control | CSV 导出保留表头 | CSV 表头 | 命中 |
| Paraphrase | CSV 导出保留表头 | 把支出记录输出成表格文件 | **漏召回** |
| Control | 水果采购预算控制在 60 元 | 水果预算 | 命中 |
| Paraphrase | 水果采购预算控制在 60 元 | 这次采买尽量少花钱 | **漏召回** |

## 3. 解释

当前检索是**词面匹配**，不是语义匹配：

- “芒果过敏”与“安全食物/身体不适”没有共享 bigram；
- “全身锻炼”与“复合动作”没有共享 bigram；
- “文笔”与“文字质量”、“情感”与“感情线”没有共享 bigram；
- “CSV/导出/表头”与“表格/输出”没有共享 bigram；
- “预算/60 元”与“少花钱”没有共享 bigram。

Control 5/5 说明检索链路本身正常；漏召回发生在改写/同义词没有词面重叠时。

## 4. 影响

- 用户必须手动勾选未被推荐的 note，或改写任务措辞。
- 项目里的“最近项目 note”回退可能偶然救回一部分项目 note，但并不理解语义；全局偏好和老 note 更容易被漏。
- 修复 pinned 无条件注入后，精度提高，但这个召回缺口更明显——之前的“总是注入”实际上掩盖了语义检索能力不足。
- 当前版本不能宣称“理解语义上下文”，只能宣称“基于显式/词面上下文的检索”。

## 5. Aliases 小实验

已实现最小版本：

- `notes` / `global_notes` 增加 `aliases_json`（schema v3）。
- 别名会进入 FTS 索引，也参与本地关键词/bigram 匹配。
- 全局 note 创建表单和任务结果接受表单可以填写别名，每行一个。
- 真实数据已备份后迁移到 v3；现有 note 的 aliases 为空。

实验结论：

- `plain`：改写召回 0/5；
- `aliases`：改写召回 5/5；
- 控制组保持 5/5，说明别名没有破坏精确匹配；
- 别名不是语义模型，只在“用户预先写入了另一种措辞”时生效。

## 6. 可选后续

| 方案 | 召回提升 | 成本/风险 | 建议 |
|---|---|---|---|
| 手动选择（现有） | 取决于用户 | 零开发；需要操作 | 立即可用，作为兜底 |
| Note aliases/tags（已实现） | 对已标注场景 5/5 | 低到中；需要用户维护标签 | 已采用，继续积累 |
| 小型同义词/领域词典 | 对固定领域有效 | 低；规则脆弱、难维护 | 可做有限领域 |
| 本地 embedding + hybrid search | 语义召回更好 | 中到高；模型/依赖/隐私/性能 | 若真实漏召回仍然频繁，再做 spike |
| 用 CLI/模型对候选 note 重排 | 语义判断更好 | 成本/延迟/隐私；每个任务额外调用 | 可选，后置 |

### 推荐顺序

1. 用 aliases 维护高价值、经常被改写的 note；保持手动选择兜底。
2. 观察别名是否能覆盖真实漏召回；不要给所有 note 堆宽泛标签，否则会引入新噪声。
3. 如果仍有大量语义漏召回，再评估本地 embedding；不要因为一次实验直接引入向量数据库。

## 7. 结论

**纯关键词/bigram 会漏；aliases 可以显著补偿，但它不是语义理解。**

- 未加别名：control 5/5，paraphrase 0/5；
- 加别名后：control 5/5，paraphrase 5/5；
- 代价是用户维护标签，且标签过宽会增加误召回。
- 当前版本应把“手动选择”和“高价值 note 的 aliases”作为一等能力，而不是宣称具备通用语义检索。
